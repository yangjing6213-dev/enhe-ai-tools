## 3. 支付通道最终决策

### 3.1 支付网关

支付宝与微信支付均通过同一个“易支付 / ZPAY”网关接入，不分别接入支付宝官方 SDK 与微信支付官方 SDK。

两种支付方式共用同一组网关 API 配置：

- 同一 API Base URL
- 同一商户标识 `pid`
- 同一商户密钥 `key`
- 同一签名算法与回调入口

仅通过请求参数 `type` 区分：

- 支付宝：`alipay`
- 微信支付：`wxpay`

前台默认选中支付宝，用户可切换微信支付。

### 3.2 页面跳转支付

首选使用服务端生成签名后的 POST 表单提交到：

`https://zpayz.cn/submit.php`

禁止把商户密钥发送给浏览器。可以把已生成的签名和支付参数提交给支付网关。

核心参数：

- `name`
- `money`
- `type`
- `out_trade_no`
- `notify_url`
- `pid`
- `return_url`
- `sign`
- `sign_type=MD5`
- `cid`、`param` 仅在真实需要时使用

### 3.3 商户订单号

支付网关的 `out_trade_no` 必须：

- 每笔支付尝试唯一
- 最多 32 位
- 符合网关实际格式要求
- 与 ENHE 内部订单主键分离

不得为适配支付平台而修改 ENHE 内部订单的主键设计。应新增或复用独立的 provider out-trade-no 字段。

### 3.4 支付金额

- 金额只由服务端根据价格快照与有效优惠券计算
- 使用精确十进制定点类型，不使用浮点数计算金额
- 最多两位小数
- 回调金额必须与订单的实际应付金额完全一致
- AI 探索入场券抵扣后，以抵扣后的金额发起支付和校验回调

### 3.5 异步通知与页面返回

- `notify_url` 是唯一可触发“支付成功”的主要入口
- `return_url` 只负责浏览器返回与展示“正在确认支付”，不能直接更新订单为已支付
- `notify_url` 与 `return_url` 均不依赖查询参数识别订单；通过 `out_trade_no` 查询服务器订单
- 当前网关通知方法按文档支持 GET，回调路由必须按真实协议实现

### 3.6 回调验收条件

收到回调后必须依次完成：

1. 校验 `sign_type`
2. 按网关规则重算并验证 MD5 签名
3. 校验 `pid`
4. 校验 `out_trade_no`
5. 校验网关 `trade_no`
6. 校验 `type` 为 `alipay` 或 `wxpay`，且与支付尝试一致
7. 校验 `trade_status === TRADE_SUCCESS`
8. 校验商品金额与服务器实际应付金额完全一致
9. 使用事务和唯一约束保证幂等
10. 订单已处理时直接返回成功，不重复发券、核券、开通权限或发通知
11. 在网关要求的时间内返回纯文本 `success`

### 3.7 主动查单、退款与补偿

系统必须实现或验证：

- 按 `out_trade_no` 或 `trade_no` 主动查询订单
- 支付确认中订单的定时补偿
- 回调失败或权限开通失败的重试
- 退款请求与退款结果记录
- 每日或定期支付对账
- 异常金额、重复回调、支付成功但权限未开通的告警

调用查询接口时，商户密钥只能存在于服务端；不得把包含 `key` 的完整 URL 写入普通日志、分析事件、浏览器或错误页面。

### 3.8 环境变量

优先复用现有 ZPAY 配置名称；若需要统一，目标契约为：

- `ZPAY_BASE_URL`
- `ZPAY_PID`
- `ZPAY_KEY`
- `ZPAY_DEFAULT_METHOD=alipay`
- `ZPAY_NOTIFY_URL`
- `ZPAY_RETURN_URL`
- `ZPAY_CID`（可选）

本阶段只允许检查变量名称和配置缺口，不读取、打印、复制或提交真实值。

### 3.9 旧付款凭证链路

- `PaymentProof` 历史记录只读保留
- 新订单停止上传付款凭证
- 新订单停止人工审核付款
- 未结旧订单的迁移策略必须单独形成清单
- 在新版支付状态机稳定前，不物理删除旧表、旧文件或旧记录
